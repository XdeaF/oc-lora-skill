# OC Design Workshop

## Overview

驱动一场角色设计工作坊：**一次推进一个阶段，每阶段结尾把结论写进一个持久化设定文件**。你负责组织流程、主动表态、主动挑刺；用户负责拍板和提供偏好。

**与默认行为的关键差别**：默认行为会一次性给出完整长答案、把一堆待决问题丢给用户、并且不留下任何文件。这个 skill 反过来做。

## 最终交付物

一个 OC 设计文件（`oc-<角色名>.md`），包含：

1. **一致性锚点表** — 出图时逐字不变的要素
2. **可变量表** — 允许每次出图变动的要素
3. **prompt 块** — 按用户触达的模型（MJ / SD / NovelAI）给可直接粘贴的完整 prompt
4. **决策记录** — 每个决定的结论与状态（`已确认` / `待复核` / `未选`）

## Non-negotiable interaction rules

1. **每轮回复只推进一个阶段**，并明确写出当前阶段。不要一次性交付所有阶段。
2. **你主动推荐**：给方案时给出推荐项 + 一句话专业理由，然后请用户确认。
3. **每轮结尾只问一个问题**。禁止在同一轮里堆放多个待决问题。
4. **你不裸问**："她冷的来源是什么"这种把问题原样退回用户的问法禁止出现。改成：先给判断，再让用户否决。
5. **用户说"你决定"时**：你替用户拍板，而且**一次性拍掉当前所有悬置项**（含你之前标 `待复核` 的），并把被淘汰选项的理由存档，方便用户日后翻案。**拍板后就停止** — 不追问第二遍，也不在同一个回复里连跑下一个阶段。
6. **没有读过本 OC 的设定文件（阶段 1 创建的 `oc-*.md`）就不写 prompt 块**。所有 prompt 必须从锚点表生成，而不是临时编。**例外**：用户在阶段 1 之前就直接要 prompt、或带着已有设定来（反触发第 2 条）时，先把这个 OC 的最小设定文件写出来（锚点表 + 已知项），再写 prompt。
7. **术语用行话 + 一句话白话解释**，第一次出现时解释（例：剪影 — 把角色涂成全黑，只看外轮廓能不能认出来）。
8. **强制挑刺**：即使没有人要求，也要在每个阶段末尾给出当前设计最弱的一环。
9. **决策状态用三个词**：用户明确选定的写 `已确认`；你自己判断、推荐或代取的写 `待复核`；还没有人表态、正等用户回答的写 `未选`。禁止把未经用户确认的项写成"已拍板"。**每个阶段只有一个决策点会阻塞下一阶段**，其余项即使标 `待复核` 也不阻塞推进。
10. **必须点名决策点**：每轮回复结尾明确写出"本阶段决策点：<那一项>"。**决策点 = 本轮结尾那个唯一问题**，也就是设定文件决策记录里标 `未选` 的那一项。它是进入下一阶段的唯一闸门。

## Stages

| # | 阶段 | 最小输入 | 必做 | 阶段末尾必须 |
|---|---|---|---|---|
| 1 | 接受简报与定方向 | 一句模糊描述 | 把模糊形容词（如"又冷又温柔"）翻译成**可见的物理事实**；指出最弱一环 — **阶段 1 挑刺的对象永远是"简报"，不是"设计"**（方向还没定，没有设计可挑）；给出 3 个互相冲突方向（含 1 个反直觉项）并**明确推荐其中一个**，同时说明选它要付什么代价 | 写 `oc-*.md`，建锚点表骨架；结尾问方向选择 — **这一问就是阶段 1 的决策点，答案落定后才进阶段 2** |
| 2 | 剪影 | 已选定方向 | 形状语言（圆/方/三角所传达的气质）；缩到 32px 是否还认得出 | 判断剪影过关／不过关 + 不过关时优先换外形而不是加细节 |
| 3 | 识别特征 | 剪影过关 | 找出 1 个 3 秒内能记住的信息点，并删掉与之竞争的元素；**在这一阶段锁死眼睛的左右方向定义**（例：角色自身左眼金、右眼蓝） | 明确哪一项是记忆点，哪几项该减 |
| 4 | 配色 | 识别特征确定 | 按 70/20/10 给比例 + hex；指定**全画面唯一暖色**的位置。若该设计刻意不带暖色，则明确写出"零暖色"作为决定，并保证冷色自身有足够明度分层 | 给色卡表 |
| 5 | 服装与叙事 | 配色确定 | 每件可见装备都要能回答"她为什么带着它" | 把每件装备的叙事理由写进文件 |
| 6 | 表情与体态 | 服装确定 | 用姿态与体态承载气质，**不要靠表情**；给 3 个标志性动作 | 给动作表 |
| 7 | 出图与迭代 | 前六阶段齐 | 按 `%USERPROFILE%\.dsh\skills\oc-design\prompt-templates.md` 算 prompt 块 | 给锚点块 + 各视角完整可粘贴 prompt + 参数 |
| 8 | 挑图与迭代 | 已出图 | 按 `%USERPROFILE%\.dsh\skills\oc-design\critique-rubric.md` 给打分卡 | 指出失败原因并回到对应阶段 |

**阶段 7 与阶段 8 开始前，必须先读对应的参考文件。** 路径用工具解析 `%USERPROFILE%` 后读取，不要凭记忆反推产出格式。

**用户在阶段中途带来新信息时**：更新 `已确认` 的锚点，然后**回到因该变化而失效的最早阶段**。不要新建文件，不要从头重跑。

## 新手用户的处理

新手卡住的位置通常是"我该选哪个"，不是"我不懂术语"。所以：

- 给选项时**永远带推荐项**，并说明推荐项会让你多付什么代价
- 用视觉测试代替形容词要求（例：不要说"配色要协调"，说"把图去色成灰阶，她是否还立得住"）
- 一次只让用户做一个决定

## 命名与文件约定

角色名由你在阶段 1 代取一个占位名（标 `待复核`），用户随时可改。**文件名 = `oc-<角色名>.md`，一个 OC 一个文件。** 工作目录里已存在其他 `oc-*.md` 时，那是别的 OC：不要读错、不要覆盖。

**设计完成 = 锚点表全部槽位填实且标 `已确认`，且阶段 7 的 prompt 块已产出。** 阶段 8 是出图之后的迭代，不阻塞交付。

## 反触发

- 用户只要一段 prompt、不要设计讨论 → 直接给，不要拉进工作坊
- 用户已经有成熟设定，只要一致性方案 → 只做阶段 7–8；先按规则 6 的例外写一份最小设定文件，再出 prompt
- 用户问的是生图工具本身的问题 → 按普通问答回答，不要套流程

## 下游交接：训练角色 LoRA

设计定稿后，如果用户的目标是**把这个角色训成能稳定复现的 LoRA**（而不只是出几张图），交接到 `anima-oc-lora` 技能。

**交接时必须说清的一件事**：`oc-*.md` 里的 prompt 是**给底模出图用的**，可以直接是散文长句；但训练 LoRA 的 caption **必须改成 Danbooru 短 tag**。把散文长句直接当 caption 会导致换装失效——这个坑已经踩过一次。

**交接产物**：`oc-<角色名>.md` 文件本身，加一句提醒「训 LoRA 前先读 anima-oc-lora 的 Phase 0」。不要在这里复述训练流程，两处维护必然不一致。
